## 需求一：宽屏布局再调整（两列 + 高度填满 + 卡片边框）

1. **最多两列**：宽屏时固定最多两列，不要 4.2 那样窗口越宽列数越多（1800px 三列、2600px 五列没必要）。
2. **高度自适应填满（本需求的重点）**：各组高度不一样，现有按行对齐的排法会让矮组下方留出大片空白高度。改成「见缝插针」的排法：有空间就排满，后面的组自动补进前面的空位，不留那么多空白高度。
   - 拖拽排序与新排法是否冲突，**开发时实测再说**（用户 2026-11-18 拍板：先按高度填满做，拖拽的问题后面测试再定）。若实测确实冲突，先把结果报用户再决定取舍，不许悄悄把拖拽弄坏。
3. **卡片边框**：组与组之间的分隔改成卡片式——每个标签组做成一张带边框的卡片，边框清晰、卡片之间留间距，既分隔显眼又美观。范围：首页与回收站的标签组列表。

## 需求二：修 OneTab 导入丢最后一组（用户确认要修）

- 现象：OneTab 格式导入靠「空行 = 上一组结束」分组；粘贴的文本如果最后一段后面没有空行（写到最后一个链接就结束），程序会以为最后一组还没写完，把它整组丢掉且不报错。OneTab 官方导出末尾自带空行，正常使用碰不到，自己编辑或从别处复制的文本可能踩到。
- 来源：原版就有的行为，不是 4.2 引入的。
- 改法：导入时把文本末尾没收尾的最后一组也正常收进来，一组都不能少。

## 需求三：修双版本共存时管理页互相抢占（用户 2026-11-18 发现并确认要修）

- 现象：同一个浏览器同时装了原版（商店 3.1）和新版（4.x）时，先打开哪个版本的管理页，另一个版本的管理页就打不开——点了只会跳回先打开的那个标签页并刷新。
- 查实的原因（已核对代码）：两个版本地址并不相同（各自有独立编号）。原版后台代码打开管理页前会先查「workbench.html 是否已打开」，查询写的是通配 `chrome-extension://*/workbench.html*`，不分版本——任意版本的同名页面开着都算「已打开」，于是直接聚焦并刷新那个标签页，不再开自己的。位置：`js/background.js` 的 openBackgroundPage 与 reloadBackgroundPage 两处（约 761、776 行），所有打开管理页的入口都走这里。原版就有的写法，新版继承。
- 改法：两处查询都带上本扩展自己的编号（chrome.runtime.id），只认自己那一份管理页。改动小、范围明确。
- 验收要点：同一浏览器同时装原版与 4.3 后，两个版本的管理页能各自打开、互不抢占；单独装一个版本时打开/刷新管理页行为不变。

## 需求四：时间改跟标签走（用户 2026-11-18 提出）

- 现状（已核对代码）：时间只有分组有一份（分组的创建时间），显示在分组那一栏；每条标签身上没有任何时间字段（标签对象只有标题和网址）。
- 改法：
  1. **每条标签加自己的「添加时间」**：新增字段记在标签对象身上（只加新字段、不动旧字段，符合红线）。收集新标签、两种格式导入等所有新建标签的入口，都在生成那一刻打上当时的时间；同一组一起收集的标签时间相同（就是收集那一刻），没问题。
  2. **显示位置调换**：主列表、搜索结果里，每条标签后面跟上它自己的添加时间（格式与现在分组时间一致，小字弱化显示），分组那一栏不显示时间。**回收站里有两个时间**（用户 2026-11-18 纠正）：每条标签后面跟它自己的添加时间；分组那一栏显示**删除时间**（这一组被删进回收站的时刻，即 deletedAt），不是分组的创建时间。
  3. **时间跟着标签走**：拖拽换组、删进回收站、从回收站还原、备份/恢复，都不改变这条标签的时间（时间存在标签自己身上，天然跟着走；开发时逐项验证）。
  4. **老标签补时间**（用户 2026-11-18 定）：4.3 之前存的标签没有自己的时间，转换时把所在分组的时间复制填充为每条标签的添加时间、落成标签自己的字段（只加新字段，符合红线）。收集来的组，分组时间本来就是这批标签的收集时间，基本准确；补完之后时间就长在标签身上，拖到别的组也跟着走、不再变。
  5. **回收站的删除时间与倒计时**：回收站分组栏按上一条显示删除时间；「还剩 X 天自动删除」本来就是从删除时间推算出来的，改为小字跟在删除时间后面保留，信息不丢。

## 需求五：回收站的分组菜单精简（用户 2026-11-18 提出）

- 现状（已核对代码）：回收站里每个分组后面跟的菜单和首页差不多，一共 6 个：打开整组、删除整组、锁定/取消锁定、置顶/取消置顶、命名该组、还原整组。
- 改法：回收站只保留 **打开整组、删除整组、还原整组** 三个；去掉 **锁定/取消锁定、置顶/取消置顶、命名该组**（回收站里的组不需要锁定、置顶、改名）。首页的分组菜单保持不变，六个都在。
- 补记（2026-11-18，用户看 4.3 总汇报时拍板）：回收站里删除整组、还原整组、删单条不再被「锁定」挡住——带锁定状态经 Gist/备份进入回收站的组原先会卡住删不掉、还原不了，现已放行；还原回首页后锁定状态原样保留，首页的锁定拦截不变。实测 e2e_lockbin 15 项全过。

## 需求六：日志页改版（分类、每条一行、详情点开）（用户 2026-11-18 提出）

- 现状（已核对代码）：日志页上半部分是原版的详细过程日志（Gist/WebDAV 每次操作一步一行，像用户贴的那段 Gitee 拉取过程，一次就十几行），下半部分才是 4.2 的操作日志——过程日志一多，操作日志被顶到页面最后面，很难找；操作日志本身也是全部平铺（最多 500 条），没有分类。
- 改法：
  1. **日志页分成几个大类分区**：Gist 备份、WebDAV、导入/导出、操作日志。归类口径：操作日志的条目按动作分到对应区（Gist 推送/拉取进 Gist 备份区，WebDAV 上传/恢复进 WebDAV 区，导入/导出进导入/导出区，其余如回收站清理、数据转换等进操作日志区）；Gist、WebDAV 的详细过程日志分别挂到 Gist 备份、WebDAV 区。
  2. **每个大类只显示最近 5 条**，下面有「查看更多」，点开才显示该类其余的（仍受日志保留天数/条数上限约束）。
  3. **每条日志只有一行**：时间 + 动作 + 成功/失败，一行完事。
  4. **详情点开才看**：过程日志每次操作收成一条一行，点开才展开全部步骤明细（就是用户贴的那种一步一行的内容，收进详情里）；操作日志的失败原因等详情同样点开才展开。
  5. 日志清理设置（开关、保留天数、最多条数）保留在日志页，位置跟着分区布局调整，别丢。

## 需求七：修拖拽开关一拨就被弹回首页（用户 2026-11-18 验收 4.2 时发现，确认加进 4.3）

- 现象：在配置页拨「是否拖拽标签组 / 是否拖拽标签」任一开关，页面立刻整体刷新并跳回首页。设置本身已保存生效，只是人被弹走。
- 查实的原因：这两个开关的 change 处理末尾有一句 refresh()（整页重载）。原版这两个开关挂在首页菜单上，改完重刷首页列表是顺理成章；4.2 把开关搬进配置页时这句刷新被原样带了过来，而本页重载后默认显示首页，于是被弹回首页。属 4.2 搬家引入的毛病。
- 改法：去掉两个开关处理末尾的 refresh()。已核对首页与回收站每次渲染列表都会重新读 dragType 设置，回到首页时新方式自动生效，不需要重载。改完拨开关应停留在配置页、照常出「已保存」提示。

## 需求八：修配置页单选点文字存不上（用户 2026-11-18 验收 4.2 时发现，确认加进 4.3）

- 现象：在配置页想把「左键点击打开时删除」选上，点选项文字后看起来选中了，但不生效；刷新页面又回到「不删除」。同页的「发送后打开后台页」单选组同样的毛病。
- 查实的原因：两组单选的 label 都写了 for 属性、指向一个不存在的 id（input 只有 name 没有 id）。点文字时浏览器不会把点击转给单选钮，原版一段老代码手动把钮「假装选中」（只改 checked、不触发 change 事件）；原版靠「保存配置」按钮读页面状态所以没事，4.2 改成 change 事件驱动的自动保存后，点文字永远存不上。点小圆圈本身是好的（原生 change）。属 4.2 改造引入的回归，自测点控件没模拟点文字而漏检。
- 改法：让点文字和点圆圈都能真正触发保存（给 input 补上与 for 对应的 id 或去掉悬空 for，并保证那段手动选中代码补发 change 事件，二者取稳妥做法）。两组单选都修。验收：点文字切换 → 出「已保存」提示 → 刷新页面仍是新选项 → 实际打开标签验证删除行为符合设置。
- 临时办法（4.2 现行）：对准小圆圈点就能存上。

## 需求九：修左键打开并删除后画面不刷新（用户 2026-11-18 改变决定，改为要修）

- 现象：开着「左键打开时删除」时，点开单个标签（或打开整组），数据立刻就删对了，但屏幕上的列表偶尔不跟着刷新，那条（组）还留在画面上，要切到别的页面再回来、或刷新一下才消失。
- 来源：原版就有的毛病（删除后的重新渲染与异步保存之间有竞态，偶尔渲染没跟上），不是 4.2 引入的。用户先前说没感知、先不管；实际开上删除模式用起来后感受到了，2026-11-18 改为要修。
- 改法口径：删除动作完成后，立即、稳定地把条目从画面上移除，把保存与重渲染的先后关系理顺，不能再偶尔复现。验收：开删除模式连续点开多个单个标签和整组，每次画面立即更新；再核对数据，删掉的确实没了、没删的都在，不误删不多删。

## 需求十：性能整体优化（用户 2026-11-18 验收时发现并要求整体处理，数据量约 719 组 / 3063 条）

- 现象：点某个分组的「锁定该组 / 取消锁定」，反应明显迟缓，要等一下状态才变；用户随后确认「置顶 / 取消置顶」同样迟缓（置顶还要多一步把组搬到最前，只会更慢），2026-11-18 09:27 又确认**删除动作（删组/删条）也非常卡顿**，并要求类似的性能问题整体优化，不要逐个打补丁。用户数据量：总共约 3000 条标签，该组 31 条。
- 查实的原因：这是个通病——只改一处的小操作，现有代码普遍走全量动作：把全部 719 组 / 3063 条整体序列化（约 1.1MB）重写一遍存储，再把整个列表从存储重读、解析、整页重新渲染一遍。数据越多越慢，和改的那一组本身有多大无关。已确认同病的入口包括 vm.updateGroup（锁定、置顶、改名、备注）以及删单条、删整组、拖拽保存等列表操作；列表本身在 3000 条量级下的打开、滚动、搜索输入也需要一并检查。
- 改法口径（整体优化）：
  1. 凡是只改一个组或一条标签的操作（锁定、取消锁定、置顶、取消置顶、改名、备注、删单条、删整组、还原、拖拽排序等），画面只更新受影响的那部分，不再整页重读重画；状态变化立即上屏，保存放后面异步完成。
  2. 保存路径避免不必要的全量重读：能直接用内存里已有的数据落盘的，不再先把全量数据从存储读一遍回来。
  3. 大数据量下列表本身的流畅度一并梳理：打开管理页、滚动、搜索框输入实时过滤不明显卡顿。**优化基准按 3 万条标签设计**（用户 2026-11-18 开工时定，约为其当前数据量的 10 倍）：列表显示可以分页或分批渲染来减负（用户认可分页思路），但**搜索必须是全量搜索**，不能只搜当前页/当前批。与需求一的两列见缝插针布局如何配合（分页边界、跨页排版），开发时定并在汇报里说明。
  4. 边界：只优化速度，不改任何功能行为、不改数据格式；与需求九（删除后画面刷新）同源，相邻代码一并理顺。
- 验收：以约 700 组 / 3000 条的数据量逐项实测——锁定、置顶、改名、删单条、删整组、拖拽排序、打开管理页、搜索输入——逐项无明显停顿、状态立即正确；再以 3 万条造数实测打开管理页、滚动、搜索与上述操作仍可接受；刷新后数据与状态保持，核对无误、无丢失。

## 需求十一：顶栏布局再调整（用户 2026-11-18 验收 4.2 时提出，已实测核对现状）

- 现状（实测 1100px 宽）：顶栏被装在一个居中的固定宽盒子里（Bootstrap 容器在中等宽度是 970px 定宽居中），左右各空出约 90px，品牌没有贴到最左、菜单没有贴到最右；主题图标在第二行中间；两行菜单只是右端对齐，上下两行的项目列对不齐、错着位。
- 改法（用户定的结构）：
  1. **品牌固定最左、菜单固定最右**：顶栏改通栏，左右只留小边距（约 12–16px），任何窗口宽度下品牌贴左、菜单贴右。**顶栏下面的内容区保持现状**（用户 2026-11-18 明确）：优先整体居中；宽屏时按需求一扩展为两列，是整块居中、每组内部仍左对齐。不要求内容区与顶栏通栏对齐。
  2. **中间全部给搜索框**：品牌和菜单之间的空间全由搜索框填满，搜索框宽度自适应伸缩。窗口变宽变窄时布局结构不变、只有搜索框变宽变窄，避免顶栏在不同宽度下反复重排跳动。
  3. **主题图标移到右上角**：放到右侧菜单第一行的最末端（回收站之后），即整个顶栏的右上角位置。
  4. **两行菜单对齐**：两行等宽、两端对齐、行内项目均匀分布，上下成行成列，不再错位。
  5. **品牌旁加仓库图标**（用户 2026-11-18 追加）：品牌名「NJ-Tab」点击仍是回首页；在品牌名旁边再加一个 GitHub 仓库图标，点击在新标签页打开用户的仓库 https://github.com/NJYZ96/NJ-Tab 。
- 验收：分别在约 880 / 1100 / 1440 / 1920px 宽度下看顶栏——品牌贴左、菜单贴右、搜索框填满中间、主题图标在右上角、两行对齐；拖动改变窗口宽度时只有搜索框宽度变化，顶栏不跳动、不遮挡。

## 需求十二：导入导出页把导出提到顶部（用户 2026-11-18 验收时提出）

- 现状：导入导出页从上到下依次是「导入 OneTab 格式」「导入默认格式（含导入备份文件）」「导出」，导出排在最后。
- 改法：把「导出」整块（导出文本框 + 导出到本地文本 / 导出为网页 / 导出备份文件三个按钮）提到页面最顶部，两个导入块依次排在它后面，导入块之间顺序不变。功能不变，只调顺序。

## 需求四补充（更正版，用户 2026-11-18 09:13 纠正，取代先前记反的版本）

- **4.3 导出的文本要带上时间属性**：每条标签在导出文本里附带它自己的添加时间；导入这种文本时能把时间读回来、恢复成每条标签的添加时间，文本导出再导入一圈，时间不丢。
- 旧记录（4.3 之前）没有逐条时间：转换时用所在分组的时间复制填充为每条标签的添加时间（与需求四第 4 条一致）。
- 兼容：没有时间字段的旧版文本（4.2 及更早导出的、以及别处来的纯文本）照样能导入，导进来的标签按分组时间/导入时刻的既有规则处理。

## 需求十三：日志页状态悬停提示对不上（用户 2026-11-18 验收 4.2 时发现）

- 现象：在日志页，顶栏状态文字显示的是日志条数（如「N条」），但鼠标悬停上去，提示还是首页那句「已存：X组 / Y条」。
- 查实的原因：显示日志的代码（showAllLogs）只改了状态文字、没改悬停提示，首页写下的悬停内容残留了下来。首页和回收站都是文字与悬停成对写的，只有日志页漏了悬停这一半。
- 改法：哪个页面显示什么文字，悬停提示就同步成对应口径（日志页悬停显示日志口径的信息）；顺带检查所有页面之间来回切换，文字与悬停都成对更新、不残留上一页的。

- 现象：4.2 里导出一份完整备份（.json），随后导入同一份文件，提示「这个备份文件格式不正确，没有导入任何数据」，一份都没导进来。导出、导入都是本插件自己的功能，自家文件被自家拒绝。

  1. 单条异常不能废掉整份备份：校验改为逐条宽容处理，异常条目跳过或修正后导入，并在结果提示里写明跳过了几条、是什么问题。

## 需求十八：清掉扩展错误页的两类报错（用户 2026-11-18 从扩展程序错误页回报）
