### 4.6.5-1　拉取点取消后的收尾三问题

**来源/现象**：原 4.6.3-2 审核意见：令牌正确时点拉取、在确认框点取消——灰色的取消弹框一闪而过；页面刷新跳到主页；日志里多了一条标题为「手动从仓库拉取成功」的日志，详情却是「已取消拉取」，标题和详情对不上。

**方案/原因**：实际原因三处：一是拉取收尾时保存过程日志的函数被传了「要刷新」，它写完日志就整页刷新——灰框刚弹出就被刷新销毁、页面也被带走；二是过程日志的成败判定只看步骤里有没有「失败」字样，取消的步骤写的是「已取消拉取」、不含失败，于是被判成成功，标题就成了「手动从 GitHub 拉取 · 成功」。修法：拉取收尾改为不刷新；成败判定先判取消——取消时存「取消」标记，日志行显示灰色「手动从 GitHub 拉取 · 取消」；以前的老日志也会按步骤内容自动判成取消显示。灰框本身就是 6 秒规则，不再被刷新打断后自然停满 6 秒。

**验收**：拉取确认框点取消：灰色弹框停留约 6 秒自动关；页面停留在 Gist 页不刷新；日志新增一条灰色「手动拉取 · 取消」，不再出现标题写成功的取消日志。

### 4.6.5-2　推送、拉取出错时两个弹框冲突、推送失败不记日志

**来源/现象**：原 4.6.3-2、4.6.3-3 审核意见：故意填错令牌点推送、输 Y 确认后，先弹旧的报错框（「获取所有 Gist 时报错了」），30 秒后又弹红色推送失败框，两个框冲突；而且日志里没有手动推送失败的日志。填错令牌点拉取也一样：先弹旧报错框（「根据 Gist ID 拉取 Gist 报错了」），又一个红色弹框一闪而过，还刷新到主页。

**方案/原因**：实际原因：推送、拉取的请求出错分支还在用上游老代码的独立报错框（「获取所有 Gist 时报错了」「根据 Gist ID 拉取 Gist 报错了」），这是第一个框；同时「列出全部 Gist」那一步出错后没人清任务状态，监视器只能等满 30 秒超时才弹红色失败框，这是第二个框；这条路径上也确实没写失败日志。修法：删掉推送、拉取全部出错分支里的旧报错框；所有出错分支统一改为：写一条带人话原因的过程日志、写一条失败简条日志、立刻清任务状态——监视器随即只弹一个红色结果框（带明确错误原因），不再等超时；顺带补上 Gitee 拉取成功时缺失的简条日志、无备份文件与内容损坏等分支的失败日志。

**验收**：填错令牌推送：输 Y 后只弹一个红色失败框（不等 30 秒），日志里有手动推送失败记录；填错令牌拉取：只弹一个红色失败框，页面不刷新，日志里有手动拉取失败记录。

### 4.6.5-10　首页跳页输入框无法输入

**来源/现象**：南极写在审核报告文末的新增问题：首页末尾「跳转到第几页」的输入框现在无法输入；回收站和搜索页实测正常。

### 4.6.5-11　WebDAV 恢复失败的日志只有裸错误码、没有具体类别

**来源/现象**：南极 2026-11-22 审核 4.6.5 时实测：WebDAV 没填密码时尝试恢复，日志记「WebDAV 恢复 · 失败 · HTTP 429」、详情也只有「HTTP 429」；填错误密码时记「HTTP 401」，同样只有裸错误码。南极定：标题不应该只有错误代码，错误代码应该带具体类别（像 Gist 那边「HTTP 401：令牌无效或已过期」那样一看就懂）。

**方案/原因**：已查明（待南极确认后动手）：WebDAV 的请求失败时，代码直接把「HTTP 加状态码」当报错文本抛出，恢复、上传、强制备份、删版本的失败日志和弹框都原样用这句，所以只有裸码；已有的 WebDAV 状态码人话表只接在连接测试上、且表里还没有 429。另外日志标题行现在会把详情前 80 字拼在标题后面（只有导入导出区在 4.6 需求九时豁免了），所以错误码还漏进了标题行。

南极 2026-11-22 已确认模板，并定下标题行规矩：**标题里只有类别和是否成功，不出现错误码；错误码和类别说明都只放详情里，点开才看。** 模板格式与 Gist 一致——详情写「HTTP 状态码：具体类别」，如「HTTP 401：账号或密码错误」「HTTP 429：请求太频繁，被服务器限流，请稍后再试」；弹框里也用同一句。

拟修：① WebDAV 全部失败路径统一带类别——401 账号或密码错误、403 拒绝访问（权限不足）、404 地址能通但路径不对、429 请求太频繁被服务器限流请稍后再试、5xx 服务器出错；表里没列到的其他 4xx 也给一句兜底类别，不留裸码；连不上、备份内容损坏这类非 HTTP 错误也换成人话（归一化只认已知的英文原始报错，不误伤已有的中文提示）。② 日志标题行不再拼详情：所有分区统一成「时间 · 类别 · 状态」，错误码只在展开的详情里出现。③ Gist 那边的对照表同步补上 429，保持两边口径一致。本条已先行送第三方模型看过一轮，兜底类别与归一化别误伤中文两点就是它提醒的，已并入方案。

**验收**：WebDAV 分别用没填密码、错误密码各恢复一次：日志标题行只有「WebDAV 恢复 · 失败」、没有错误码，点开详情是「HTTP 状态码：具体类别」而不是裸码；再用一个会返回 429 的场景（或连接测试）验证 429 的类别文案；上传备份、恢复前强制备份失败时同样带类别；其他分区的日志标题行也不再带详情内容。

### 4.6.5-12　文本导入把去重跳过算成失败、还逐条写进详情

**来源/现象**：南极 2026-11-22 审核 4.6.5 时用真实数据实测：默认文本导入后，日志记「文本导入 · 部分失败 · 共失败 2878 条」，详情里还逐条列出「去重跳过：……」。南极定：去重是正常处理，不叫失败；只有无法识别、无法导入的条目（比如网址为空的那种）才叫失败；去重的条目不用写详情，只有无法导入的才需要写详情。

**方案/原因**：已查明（待南极确认后动手）：导入日志的汇总函数把「去重跳过条数 ＋ 解析不了条数」加在一起当失败总数，只要有去重就标成部分失败，去重条目也逐条写进了详情（这是 4.6.3 需求十七定的旧口径，南极本次改定）。拟修：失败只认解析不了、无法导入的条目；去重只在详情第一行保留汇总数字（去重跳过 X 组 / Y 条），不再逐条列；一次导入里没有无法导入的条目时，这条日志就是成功、不标部分失败。默认文本导入与 OneTab 导入共用同一个汇总函数，两边一起改。

**验收**：拿一份大半是重复条目的文本导入：日志是成功，详情只有第一行汇总（含去重数字）、没有逐条去重明细；再拿一份混有空网址等无法导入条目的文本导入：日志标部分失败，失败条数只等于无法导入的条数，详情逐条列的只有无法导入的那些。

### 4.6.5-13　默认文本导出再导入，组数条数变多（标题带「 | 」被截断）

**来源/现象**：南极 2026-11-22 审核 4.6.5 时实测：旧数据原先 719 组 / 3065 条，导入 V4 后导出为通用文本格式、再导回来，变成 804 组 / 3221 条；同样的数据没改过，不应该有出入。

**方案/原因**：已用南极的真实数据在本地完整复现（照代码原样模拟导出再导入，结果 807 组 / 3223 条，与实测基本一致，差 3 组 / 2 条为个别条目差异）：元凶是标题里带分隔符「 | 」的标签——真实数据里有 172 条（如「某某标题 | 网站名」这类常见写法）。导出时标题原样写进文本，导入时按「 | 」切开，标题只剩第一截、添加时间也跟着丢了；而去重是按「网址 ＋ 标题」一字不差比对的，标题变了样就认不出是同一条，被当成新标签又收了一遍——模拟里多出的 158 条全部是这个原因，还连带多出 88 个新组。拟修（不改文本格式）：导入解析标签行时从两头取——第一段是网址、最后一段是时间格式的就当添加时间、中间所有段拼回完整标题；组头行同理，靠「锁定/解锁、置顶/不置顶」两个固定词定位，前面的拼回组名、后面的拼回备注；老格式文本照样兼容。附带发现：导入时还会删掉标题里的表情符号（本次数据里 0 条中招），同属「标题被改 → 认不出、还丢字」，拟一并去掉这个删除动作。

**验收**：拿这份 719 组 / 3065 条数据：导出文本再导入回同一个库，导入应为 0 组 / 0 条新数据、全部去重跳过，总数仍是 719 组 / 3065 条；再导入到一个空库逐组核对：带「 | 」的标题完整无缺、添加时间都在，总数对得上。
