## 0. 术语先行（修正 1）
- Gist 和 WebDAV 这两套东西本质都是单向备份，不是双向同步。
- 所有用户能看到的文案里，把“同步”改成“备份/恢复”类说法：如“同步功能”→“备份功能”，“是否自动同步”→“是否自动备份”，WebDAV 标题去掉“同步”字样；日志、提示、README 同步改。
- 内部存储键（如 autoSync）和函数名不改名，避免破坏已有设置和数据兼容；只改展示文案和注释说法。

## 1. Gist 备份（机制和数据不变，叫法和标识要改）
- 现状已核实：后台定时（GitHub 90 分钟 / Gitee 70 分钟检查，autoSync 开才推）只自动推送覆盖远端同一个 Gist 文件 brower_Tabs.json，从不自动拉取；手动拉取才覆盖本地。
- 本轮不改变 Gist 的备份机制和数据结构 {tabGroups, delTabGroups}，只改文案叫法（见第 0 条）；Gist 的文件名和描述标识按第 9 章做一次性迁移，迁移后只用新标识。

## 2. WebDAV 多版本自动备份（需求 4 新版）
- 自动备份：新增开关和间隔设置；后台定期检查，到期自动把本地数据备一份到远端。自动备份只上传、永不自动覆盖本地。
- 单文件多版本：每次备份是一个 json 文件，文件名带时间戳，建议 njtab-backup-YYYYMMDD-HHmmss.json（最终命名在开发阶段固定后写入测试）；每次新建文件，不覆盖旧文件。
- 备份内容带版本号：保留 formatVersion（当前 1），新增插件版本号 appVersion 和备份时间。恢复规则：无版本号或 formatVersion 大版本不符 → 直接拒绝，确认也无法绕过；备份的 appVersion 比当前插件新 → 在确认弹窗中警告。
- 手动备份/恢复保留；恢复时可列出远端历史版本并选择一份。
- 自动清理（修正 6，用简单规则）：两类规则，可同时开，任一规则保住的版本不删：
  - 保留最近 N 天内的全部版本；
  - 保留最近 N 份版本。
  只删文件名符合备份命名规则的文件，远端其他文件不碰；刚上传的版本不删。

## 3. 确认弹窗（修正 2）
- 凡是会覆盖数据的操作（Gist 手动拉取覆盖本地、Gist 推送覆盖远端、WebDAV 恢复覆盖本地），改用插件页面内的自定义美观弹窗，适配浅色/深色主题，不再使用浏览器原生 confirm/alert/prompt 那种丑弹窗。
- 现状备注（2026-11-17 复核聊天记录时查实）：Gist 的推送/拉取目前正是用浏览器原生 prompt 框、要求输入“确定”二字才执行（代码里共 4 处），这正是用户第 2 条说的“弹框输文字太麻烦”，本次一并替换为新弹窗输 Y；WebDAV 恢复目前是单次原生 confirm，同样替换并升级为 2 次确认。
- 2 次确认流程：第 1 次为普通弹窗确认（讲清操作、数据量、后果）；第 2 次必须在输入框里输入单个字母 Y，确认按钮才可用，点确认后才执行。不要求输入长文字。
- 自动备份是新增文件、不覆盖任何数据，不弹窗确认（否则自动无意义）。

## 4. 恢复前强制备份（修正 3，替代旧快照机制）
- 删除旧的 webdavRestoreSnapshot 快照机制（包括恢复按钮的原计划一并取消；升级时清理该旧键）。
- 改为：任何从 WebDAV 恢复覆盖本地的操作，开始前必须先把本地当前数据作为一份正式备份，上传到 WebDAV 成为一个带时间戳的版本（在版本列表里可见、可再恢复）。
- 恢复流程的顺序固定为：第 1 次确认 → 强制备份当前数据 → 备份成功后第 2 次确认（输 Y）→ 才覆盖本地。避免用户最后取消却白白上传一份，也避免没备份就先确认。
- 强制备份失败（网络不通、WebDAV 未配置、认证失败）→ 恢复立即中止，本地数据不动，并用新弹窗告知原因。没有备份成功，不许覆盖。

## 7. 密码安全（修正 7）
- 现状已核实：WebDAV 密码、GitHub/Gitee 的 Gist token 目前都是明文存放在 chrome.storage.local，备份文件和 Gist 内容里不含密码/token（这一点保持，任何情况下密码/token 不得进入备份文件、导出文件、Gist 内容和日志）。
- 改造要求：存储时不得明文保存。采用本机加密存储（密钥只存本机、与密文分开存放），界面上密码框保持密码样式，保存后不再把明文回填到页面。
- 必须如实告知用户的边界：浏览器插件没有系统级保险箱，本机加密能防的是明文裸奔、误泄露、被顺手抄走，不能承诺银行级安全；最终实现时在设置页用通俗文案说明。
- 迁移：老版本已存的明文密码/token，升级后首次读取时自动转为加密存储，不要求用户重新填写。
- 附带修掉：现在保存 Gist token 时用的也是浏览器原生 prompt 输入框（丑且明文回显在输入框里），一并改为页面内的密码输入框。

## 9. 一次性转换（迁移）细则（2026-11-17 用户补充）
- 总原则：旧标识只在“检测和读取旧数据”这一步出现一次；转换成功后，存储、远端、备份文件里只剩新标识，不长期双认、不保留旧属性。转换失败时保留旧标识原样，下次继续尝试，绝不因转换失败丢数据或把旧数据误判为无效。
- 本地数据：新版首次打开时检测 3.1 数据（无新字段的分片数据、明文密码/token、旧设置），按各章规则补字段、加密密码并写回；写回成功即视为转换完成，并记一条日志。
- Gist 标识迁移（顺序不能反）：
  1. 先按旧描述 myCloudSkyMonster / 旧文件名 brower_Tabs.json 找到并成功读取旧 Gist，确认数据完整（组数/标签数可核对）；
  2. 读取成功后，在同一次推送更新里把该 Gist（编号不变）改为新描述 NJ-Tab、写入新文件名 NJ-Tab_Tabs.json 并删除旧文件；
  3. 此后查找、推送、拉取只用新标识。
  绝不允许还没读到旧数据就先改名，那样会把自己的旧备份锁在门外。
- 一次性后果（用户已知并接受）：迁移完成后，原版 3.1 再也认不出这份 Gist；如需退回 3.1，只能靠迁移前的文本导出或迁移前保留的旧 Gist 副本。因此正式迁移前，实施阶段必须先提醒用户做一次 3.1 侧的留底（文本导出或保留旧 Gist 不动直到新版验证完成），验证新版数据无误后再执行第 2 步的远端改名。
- 备份文件：不存在旧备份，app 字段直接只认 "NJ-Tab"；若将来导入时遇到 app 为旧名的文件，按无效备份拒绝并提示原因（不做静默双认）。
