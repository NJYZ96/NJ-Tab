## 需求一：Gist 备份与 3.1 原版区分开（新版只从旧版拉、不往旧版推）

- 背景：新版和 3.1 的 Gist 备份要做一个区分，防止新版把旧版的备份覆盖掉——迁移完成前，旧版那份备份必须完好无损。
- 改法：
  1. **拉取兼容**：新版兼容从旧版（3.1）的 Gist 把数据拉下来，并按新版规则完成转换（补每条标签的添加时间等，沿用 4.3 的转换口径）——这是正式迁移要走的路，必须走得通。
  2. **推送不碰旧版**：新版不支持向旧版的那个 Gist 上传；推送时新建新版自己的 Gist，文件名用 `NJ-Tab_Tabs.json`，与旧版的 `brower_Tabs.json` 区分开，防止覆盖旧版备份。
- 已知现状：当前代码拉取已是新文件名优先、旧文件名兜底（先找 `NJ-Tab_Tabs.json`，没有再读 `brower_Tabs.json`）。**要紧的现状**：4.1~4.3 的推送带「一次性迁移」逻辑——推送时若发现旧版 Gist，会把它的描述改成 NJ-Tab、写入新文件并**删掉旧文件 brower_Tabs.json**，等于把旧版 Gist 整个转成新版的；本需求就是要改掉这一点。4.4 发布前，用户不要用新版往 Gist 推送（拉取是只读的、安全）。
- **推送侧已定（2026-11-19 用户拍板，选方案 A）**：**新建一个独立 Gist**。新版建自己的一条 Gist（描述 NJ-Tab、文件 NJ-Tab_Tabs.json），旧版那条一字不碰；拉取先读自己那条、没有才只读旧版那条做迁移。原方案 B（同一个 Gist 里加新文件）不用。
- **GitHub 与 Gitee 的展示差异不影响本需求（2026-11-19 查 3.1 代码确认）**：3.1 在两个平台创建时传的都是同一套标识——描述 `myCloudSkyMonster` + 文件 `brower_Tabs.json`；用户看到的差别只是两个网站的页面展示规则不同（Gitee 先展示描述作标题、点进去才看文件，GitHub 页面直接拿文件名当标题显示）。实现时不能凭页面第一眼看到的名字判断，要按接口里的描述、文件名和 Gist 编号区分。另须防本地存有旧版 Gist 编号（githubGistId/giteeGistId）时按编号直接更新旧 Gist：推送前先核对该编号对应的是新标识（NJ-Tab / NJ-Tab_Tabs.json）才可更新；核对为旧标识的只能当迁移来源只读，推送要新建独立 Gist 并改存新编号。
- 验收：用 3.1 的 Gist 在新版里拉取一次，数据完整拉下并完成转换；新版推送一次后，再去看旧版 Gist，内容与推送前一字不变（3.1 那边照常能用）；新版的数据写在新版自己的 Gist 里，之后新版拉取读的是自己那份。

## 需求二：搜索结果里的标签要能管理（删除 + 跳转到所在组）

- 现状：搜索框搜到的标签只能打开，不能管理——想删一条，还得先找到它在哪一组慢慢翻；想知道它在哪一组，也没有入口。
- 改法：
  1. 搜索到的每条标签，**行开头加两个图标**：一个是**删除**，一个是**跳转**（点跳转定位到该标签所在的那一组的位置）。
  2. 该组是锁定状态时，删除图标变成一把**小锁**：必须先点小锁解锁这条标签，然后才能点删除（单条解锁的口径与需求三一致：只当次有效）。
  3. **单独删除一个标签不需要确认**，点删除直接删；删除整组才需要确认（沿用现有的删整组确认流程）。
  4. 两个图标样式要能明显区分，**间距拉开、不要挨得太近**，避免误操作点错。
- 验收：在搜索结果里删掉一条标签（无确认弹窗、数据确实没了）；点跳转能定位到它所在的那一组；锁定组里的标签先显示小锁，解锁后才能删；两个图标分得开、不会误触。

## 需求三：主列表锁定组里的单条标签，也要能单独解锁再删除

- 现状：主列表里，如果组没有锁定，单个标签前面有一个删除图标；如果组锁定了，单个标签前面就没有图标了——想删锁定组里的某一条，只能先把整组解锁，动静太大。
- 改法：
  1. 锁定组的每条标签前面显示一把**小锁图标**。
  2. 点小锁可以**单独解锁这一条**标签，解锁后就能删除它，不影响这一组的锁定状态，也不影响组里其它标签。
  3. **单条解锁只当次有效**：如果解锁以后没有删除，那么下一次刷新页面，它会根据这一组的锁定状态自动重新上锁。单条解锁只是当次画面上的临时状态，**不落盘保存、不改数据**。
- 验收：锁定组里点某条的小锁 → 能删掉这一条，组仍是锁定状态、其它条不受影响；解锁一条但不删 → 刷新页面 → 那条又变回小锁状态。

## 需求四：删除整组的入口只留一个（组主标题前面那个）

- 现状：删除整组有两个入口——分组菜单里有「删除整组」，组主标题前面本来也有一个删除整组的按钮，重复了。
- 改法：
  1. **取消分组菜单里的「删除整组」**，只保留组主标题前面的删除整组按钮。
  2. 点「锁定该组」菜单后，组主标题前面的删除整组按钮**变成一把小锁**（表示这组删不了）。
  3. 要删除整组必须先取消锁定，两种方式都行：**点组主标题前面的小锁按钮**，或者**点菜单里的「取消锁定」**——任选其一解锁后，删除整组按钮恢复，才能删整组。
- 验收：分组菜单里不再有「删除整组」；未锁定组主标题前是删除按钮、能正常删整组；锁定后按钮变小锁、删不了；用两种方式分别解锁一次，解锁后删除按钮都恢复。

## 需求五：休眠打开修 Bug，并加「超过 N 条才休眠」的配置

- 现象（Bug）：恢复一组标签时开启「休眠打开」，打开的所有标签都是空白页，网址（域名）丢了——休眠打开目前是坏的，**必须修好**：休眠的标签被点开激活时，要能正常加载出原来的网址页面，一个网址都不能丢。
- 新增配置：
  1. 加一个配置项：**数量 N，可以自定义，默认 10**（2026-11-19 用户定）。
  2. 一组标签的数量**超过 N 时才用休眠打开**；不超过 N 的组，整组直接打开，不休眠。
  3. 用休眠打开时，**最前面的 N 条直接打开，后面的才休眠**，不是整组全休眠。
- **已定（2026-11-19 用户拍板）**：两处 N 是**同一个数**；且这个 N **只在「休眠打开」开关启用时才生效**，开关关着时恢复整组与 N 无关。
- 验收：开启休眠打开恢复一个多标签组，所有标签网址都正确、逐个点开无空白页；组内条数 ≤ N 时全部直接打开；条数 > N 时前 N 条直接打开、其余休眠，点开后都能正常加载原网址。

## 需求六：拖拽标签组和拖拽标签不再互斥

- 现状：拖拽标签组与拖拽标签是互斥的单选设置，同一时间只能开一种，想拖另一种得先去配置里切换。
- 用户看法：没必要互斥——拖标签就是把这个标签拖到另外一个标签组里面去（或在本组内换顺序），拖标签组就只是移动标签组的排序，两件事互不影响，应该没什么冲突。
- 改法：取消互斥设置，两种拖拽同时可用：**拖标签支持跨组移动与组内排序；拖组只负责组与组之间的排序**。已有数据和顺序不受影响。
- 现状细节：那两个勾选项（拖拽标签组 / 拖拽标签）在配置页和旧菜单里各有一份，背后存的是同一个 dragType 值、开一个自动关另一个（联动互斥），改的时候两处都要处理。
- **设置项去留已定（2026-11-19 用户拍板）**：**去掉这两个开关**——配置页与旧菜单两处都删，等于默认两种拖拽都打开：抓标签拖是移标签、抓组标题拖是移组，不再有任何拖拽模式设置。老用户本地存着的 dragType 值不再起作用（留着不删也行，但代码不再读它做互斥判断）。
- 验收：不改任何设置，既能把一条标签从 A 组拖到 B 组（刷新后还在 B 组、两组条数此消彼长、总条数不变），也能拖动组调整组顺序（刷新后顺序保持）；两种拖拽交替连续操作不出错、不丢数据。

## 需求七：搜索改成独立页面

- 现状：搜索是嵌在当前页面里的——在顶栏搜索框输入，搜索结果就地显示在当前页面上，没有独立的搜索页面。
- 改法：
  1. **不要内嵌结果了，改成单独一个搜索页面**：在搜索框输入搜索词、**按下回车**，整个页面就刷新成一个单独的搜索页面。
  2. 搜索页面的内容还是目前搜索结果的这些内容，**加上需求二的管理改动**（每条标签带删除/跳转图标，锁定组的带小锁）。
  3. 搜索页面同样按 **50 组一段**分段显示做性能优化（与 4.3 的分段口径一致；搜索范围仍是全量，不因分段漏掉数据）。
  4. **回收站的搜索也一样，单独成页**，并区分来源：从首页搜索框发起的搜主列表，从回收站搜索框发起的搜回收站，两边结果不混。
- 验收：首页搜索框输入词按回车 → 进入独立搜索页，结果正确且每条带管理图标；在搜索页删一条、跳转一次，行为与需求二一致；结果很多时按 50 组分段、加载流畅且不漏数据；回收站搜索同样独立成页、只出回收站的结果。

## 需求八：导入要去重

- 现象：当前导入没有去重——比如把当前版本的数据导出，然后马上原样导入回来测试，数据量直接翻倍，组和标签全多出一份一模一样的。
- 改法：导入时要去重，已经有的数据不要再重复导进来。
- **判重口径已定（2026-11-19 用户拍板）**：
  1. **判重粒度**：逐条判重——逐条比，只补本地没有的新条。
  2. **判重键**：网址 + 标题都一致才算重复（只网址同、标题不同，不算重复，照常导入）。
  3. **跨组判重**：算重复——同一条标签（网址 + 标题都一致）不管出现在哪个组里，本地已有就跳过，不再导入第二份。
  4. **适用范围**：备份文件导入、文本导入（默认格式 / OneTab）都去重；WebDAV 恢复和 Gist 拉取是覆盖式同步，不去重（维持原样）。
  5. **常驻提示语（用户追加）**：去重规则要写成提示语，**常驻**显示在可能涉及去重的导入/导出相关位置（不用弹窗形式），让用户随时能看到导入会怎么去重。
- 注：去重跳过了多少，按 4.3 需求十四已定的口径，要在导入结果提示和操作日志里写明（跳过几组/几条），不能闷声跳过。
- 验收（口径定下后按口径验）：导出当前数据后原样导入，组数、条数一点不涨；导入一份与本地部分重叠的备份，只有真正新增的数据被加进来，重叠部分不重复；去重明细在日志里查得到。

## 附：4.3 测试中发现的 2 个问题——已定纳入 4.4（2026-11-19 用户授权助手判断，助手决定两个都修）

1. **加密钥匙缓存毛病**：令牌/WebDAV 密码解密用的钥匙在后台进程里会缓存一份；若钥匙生成时存储状态不一致（例如页面与后台在钥匙不存在的瞬间同时各生成一把），后台缓存的钥匙与密文对不上，之后自动备份会一直报「令牌未保存」直到后台进程重启。正常使用极难碰到（钥匙只在第一次生成一次），4.3 测试中是人为清空全部数据才触发的。建议修法：解密失败时把缓存钥匙作废、重新从存储读一次钥匙再试一次。
2. **GitHub 与 Gitee 自动备份共用一个「忙碌」标记**：两边闹钟同一时刻触发时，先跑的占住标记，另一个会被挡下等下一轮（下一轮会补上，不丢数据）。只用一个平台的用户基本无感。建议修法：两个平台各用各的忙碌标记，互不挡道。
